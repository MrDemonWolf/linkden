This page shows how the [components](/docs/design-system/components) combine into screens and flows. The [overview](/docs/design-system) names each region of the editor and the public page; here you see how those regions behave when something is edited, saved, previewed, emptied, or signed into.

Every capture is the running app with the synthetic Rowan Ellis profile: desktop at 1440 × 900, phones at 390 × 844. A few states cannot exist on the sample stack without changing saved data: an empty block list, an empty Inbox, a failed request, the first-run wizard, and the two-factor prompt. For those, the capture script rewrites one response inside its own browser, so the real components render the state while the database stays unchanged. The captions say when this was done.

## Admin page structure

`AdminShell` (`components/admin/admin-shell.tsx`) is the client chrome around every signed-in admin page. The server layout `app/admin/layout.tsx` renders it and owns the metadata. The shell owns the session gate, the sidebar, the 64px sticky top bar, the one `main#main-content` landmark, `AdminFooter`, and the preview rail. Below 1024px it swaps the sidebar for a bottom tab bar and the rail for a preview sheet. Pages fill it through `PageShell` and `PageHeader`. They never render a second `main` or their own right-hand column.

A "Skip to main content" link is the first focusable element. The scroll padding keeps a focused field clear of the sticky top bar, the tab bar, and a save bar (WCAG 2.4.11).

The label comes from `PageHeader`'s `kicker` when the page sets one (Settings reports its section this way). Otherwise the shell passes the path segment to `subTabLabel` (`components/admin/nav-list.tsx`): `seo` reads "SEO", and any other segment is title-cased word by word (`profile` → "Profile", `two-words` → "Two Words"), matching the destination's `SubTabs` labels. - **`StatePill`**, the publication status. See [Save, discard, and publication state](#save-discard-and-publication-state).
- **Preview action**, below `lg` and only when the page registered a preview. It is an icon button named "Open live preview".
- **`SharePopover`**.
- **View live**, from `lg`: an `<a>` styled as an outline `sm` button with `buttonVariants`, so it keeps the link role. It opens `NEXT_PUBLIC_SITE_URL` in a new tab.
- **Account menu**, below `lg`, where the sidebar footer is not rendered. The menu holds identity, Account, Wallet pass, and Sign out.

Destination layouts place the header and tabs once for every sub-page. This is the Design layout, with its imports and `metadata` export left out:

```tsx title="apps/web/src/app/admin/design/layout.tsx"
const DESIGN_TABS = [
  { href: "/admin/design", label: "Theme" },
  { href: "/admin/design/banner", label: "Banner" },
  { href: "/admin/design/branding", label: "Branding" },
  { href: "/admin/design/seo", label: "SEO" },
] as const;

export default function DesignLayout({ children }: { children: React.ReactNode }) {
  return (
    <PageShell>
      <PageHeader title="Design" />
      <SubTabs items={DESIGN_TABS} ariaLabel="Design sections" />
      {children}
    </PageShell>
  );
}
```

- `PageShell` adds vertical rhythm only: 16px between children, 24px from `sm`. It has no entrance fade.
- `PageHeader` renders one `h1` in the display font: 24px, 28px from `sm`, semibold, `tracking-[-0.025em]`. An optional `badge` sits beside the title. From `sm`, `actions` move to a second column. On phones they follow the title and description.
- `SubTabs` are plain Next `Link`s styled as a tab strip. They are 44px tall, 40px from `md`, with 12px text. The strip scrolls horizontally and never wraps. The current tab gets `aria-current="page"`. The longest matching `href` wins, so a destination root never outranks its own child route.
- Every admin route has a server `layout.tsx` that exports metadata. Titles follow the `'<Page> · <Destination> · LinkDen Admin'` template.

## Preview rail and mobile sheet

An editing page hands its preview to the shell with `usePreviewSlot` and keeps its own form state. The shell renders the same registration in the desktop rail and the mobile sheet. Pages call the hook on every render, because overrides are fresh objects each time. They never read the registration back: the state and the setter live in two separate contexts to avoid a render loop.

```tsx
import { usePreviewSlot } from "@/components/admin/preview-slot";

usePreviewSlot({ overrides: { profile: { name, bio } } });
```

| Field | Purpose | Used by |
| --- | --- | --- |
| `overrides` | Unsaved `profile`, `settings`, `blocks`, or `socialNetworks` layered over `public.getPage` | Links (Blocks, Profile, Social) and Design (Theme, Banner, Branding, SEO) |
| `mode`, `onModeChange` | Control the preview's light or dark mode | Design → Theme (follows its color-mode control) |
| `preview` | A custom node that replaces `PagePreview` | Settings → Wallet |
| `size` | `"default"` or `"wide"` (425px rail) | Settings → Wallet |
| `panel` | A panel that replaces the preview at `lg` and stacks above it at `xl` | Links → Blocks (the block editor) |
| `altView` | `{ label, node }`, a second view the rail header can switch to | Design → SEO (Social card) |

The toolbar has a Light preview and Dark preview toggle (`aria-pressed`), Copy link (toast "Link copied"), and Open live page. The first mode follows `default_color_mode`, and `system` uses the browser's preference. A status line under the toolbar says what the viewport contains:

| Status line | Shown when |
| --- | --- |
| Includes block drafts | At least one shown block is still a draft |
| Preview of enabled blocks | Enabled blocks are shown and none is a draft |
| No visible blocks | Blocks are saved but none is enabled or visible |
| Sample content · no blocks yet | No blocks are saved; a Sample chip appears in the toolbar |

`PagePreview` renders the real `PublicPage`. Do not fork block markup for the preview. It takes everything except blocks from `public.getPage`. Blocks come from `blocks.list`, so enabled drafts appear before they are applied. The same feature gates as the live page apply: Connect blocks hide while the contact form is off, and vCard blocks hide while vCard is off. Saves that invalidate `settings.*`, `social.*`, or `vcard.*` queries also refetch the page data, and unsaved overrides stay layered on top. If either query fails, the viewport is replaced by `QueryError` ("Couldn't load the preview").

`PagePreviewViewport` is a plain bordered document viewport. It renders the page at 390px and scales it to the available width, measuring the scaled height so short pages keep their natural height. Long pages scroll inside a 570px cap. There is no phone bezel, clock, status bar, or notch. The content is `inert` and exposed as one `role="img"` named "Live preview of your page". The outer scroller stays outside the inert subtree, so wheel scrolling still works. Use View live for interactive checking. Responsive public content measures `.ld-page`, so a narrow inline preview never adopts the editor's desktop width.

## Save, discard, and publication state

Saving and publishing are separate steps. A save writes authoring data. Only a verified publication receipt means the public site changed.

<Screenshot
  light={unsavedLight}
  dark={unsavedDark}
  alt="Design, Theme after selecting the Forest preset: the top-bar pill reads Unsaved in amber, the Forest card is selected, the preview rail is recolored in green, and a bar at the bottom of the tool column reads You have unsaved changes with Discard and Save changes."
  caption="One unsaved edit: Forest is picked but not saved. The pill reads Unsaved, the preview already shows the change, and the save bar sticks to the bottom of the tool column."
/>

1. **Edit.** `useSettingsForm` compares the form with its saved baseline (shallow equality). While they differ, `useUnsavedChanges(true)` adds one to a module-level dirty counter.
2. **Signal.** `StatePill` reads the counter through `useAnyUnsaved()` and shows Unsaved with a warning outline. The page's `StickySaveBar` appears.
3. **Save or discard.** Save validates first, then sends only the changed keys in one `settings.updateBulk` call (one `db.batch`). It invalidates `settings.getAll` and shows the page's success toast. Discard restores the saved baseline, and the bar and the Unsaved label disappear.
4. **Leave.** While anything is dirty, one shared guard asks "Discard unsaved changes?" once. It catches in-app link clicks (capture phase, before Next handles them), Back and Forward (a Navigation API `traverse`, where supported), and reloads or closes (`beforeunload`). Modifier and middle clicks, `target="_blank"` links, hash links, and other origins pass through.

Fresh server data, such as the refetch after a save or a window-focus refetch, moves the baseline and every field you have not edited. Edited fields keep their unsaved values.

```tsx title="apps/web/src/app/admin/settings/email/page.tsx"
const form = useSettingsForm<EmailState>({
  parse,
  serialize,
  validate,
  successMessage: "Email settings saved",
});
// A failed load would otherwise leave the skeleton up forever.
if (form.isError) {
  return <QueryError message="Couldn't load settings" onRetry={() => form.refetch()} />;
}

<StickySaveBar
  isDirty={form.isDirty}
  isSaving={form.isSaving}
  hasErrors={form.hasErrors}
  onSave={form.save}
  onDiscard={form.reset}
/>
```

Use one `useSettingsForm` scope and one `StickySaveBar` per settings page. `validate` returns `{ field: message }`. While it is non-empty, `save()` does nothing and `hasErrors` disables Save:

### Publication status

`StatePill` is an outline `xs` pill in the top bar. Its label follows this order of precedence:

| Label | Shown when | Tone |
| --- | --- | --- |
| Unsaved | Any mounted form is dirty | Warning |
| Check status | The `publication.status` query failed | Neutral |
| Checking… | The status has not loaded yet | Neutral |
| Failed | Recovery is required | Destructive |
| Publishing off | Publication is not available (this sample stack: "Publishing has not been enabled") | Neutral |
| Publishing | A revision is queued or publishing; status is polled every 10s for up to 2 minutes | Neutral |
| Published | The last publication succeeded and the live page was verified | Success |
| Failed | The last publication failed | Destructive |
| Draft | Anything else: saved content that is not yet published | Neutral |

<Screenshot
  light={pillPopoverLight}
  alt="A popover titled Publish changes with the description Publishing has not been enabled, a Review block drafts link, Refresh status and a disabled Publish button, and the note At least 60 seconds between new revisions, up to 20 per UTC day."
  caption="The popover behind the pill. With publishing off, Publish stays disabled; Review block drafts opens Links with the Drafts filter."
  maxWidth={353}

The popover (320px) holds the title "Publish changes", a description for the current state, the last verified revision when there is one, scheduling notes, a "Review block drafts" link to `/admin/links?filter=drafts`, Refresh status, Publish, and the rate-limit line. Publish stays disabled when there are unsaved changes, while a request or fetch is in flight, when the status read failed or publishing is unavailable, while recovery is required, while a revision is pending, and when saved content already matches the published revision. Only successful saves of public source data mark the status stale. Keep pending, unavailable, failed, and verified states distinct, and never show Published because a save succeeded.

## Block editor

Links → Blocks edits one block at a time in a panel whose home depends on the width:

| Viewport | Where the editor opens | Page preview |

It layers a gradient and a dot texture from the pass colors. When a color is blank, `WALLET_DEFAULTS` applies: background `#091533`, foreground `#FFFFFF`, label `#0FACED`, organization "LinkDen".
- The QR code is generated in the browser with `qrcode` (240px, no margin, error correction M) under "Scan to view profile". The signed pass uses Wallet's own `barcodes[]` instead.
- An optional strip image (92px tall) sits behind the primary field, under a dark gradient.
- With back fields, a "Back ›" control flips to the reverse. It sits in its own row at the bottom-right of the front, under the "Scan to view profile" caption (or under the fields when the QR code is off), where Wallet puts its flip control, so it never covers the header fields. It is styled as a micro label at 50% opacity (full opacity on hover), and an `::after` hit area (16px above and below the label) keeps a touch target of at least 44px. On the reverse, "Front ›" sits at the top right beside the organization name; an empty reverse reads "No back-of-pass fields yet."
- Field counts and lengths come from `packages/validators/src/wallet.ts`, so the editor and the generated pass agree:

| `PASS_FIELD_LIMITS` | Header | Primary | Secondary | Auxiliary | Back |
| --- | --- | --- | --- | --- | --- |
| Fields | 3 | 1 | 4 | 4 | 20 |

Each field allows a 64-character key, a 40-character label, and a 200-character value. Context-aware relevance allows up to 10 locations (`PASS_LOCATION_LIMIT`). `resolvePassContent` resolves the same capped content for the preview and the `.pkpass` generator.

## Motion

Keep decorative entrance animations on public content, not on admin pages or forms. The preview rail's 220ms width transition and real loading indicators stay. Honor reduced motion in CSS and JavaScript: imperative smooth scrolls check `prefersReducedMotion()`. See [Foundations](/docs/design-system/foundations).
