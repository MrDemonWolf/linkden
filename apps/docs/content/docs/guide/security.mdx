LinkDen includes authentication, server-side validation, request limits, and a single-admin database constraint. Operators still need to configure deployment access, provider credentials, backups, and recovery.

## Protect first-time setup

The first account created at `/admin/setup` becomes the administrator. Subsequent signups receive 403, and a database trigger prevents a second account.

Set a random `SETUP_TOKEN` before exposing a fresh instance. The setup wizard sends it through `x-setup-token`; an incorrect token is rejected. Without it, the first-account window is open to whoever reaches setup first.

## Two-factor sign-in

1. Open **Settings → Account → Two-factor authentication**.
2. Start enrollment, scan the QR code or enter the secret in an authenticator, and verify its first code.
3. Save the backup codes somewhere separate from your device.
4. Test sign-out and sign-in before relying on the new setup.

Enrollment becomes active only after a valid confirmation code. Password sign-in then requires a TOTP or an unused backup code before an authenticated session is issued. Each backup code works once. The optional trusted-device choice lasts 30 days.

Magic-link sign-in requires configured Resend email and two-factor to be off. It serves only the existing admin, expires after ten minutes, and cannot create another account. Turning it off also blocks outstanding verification routes.

A password change revokes other sessions. Password reset revokes every session. An email change requires confirmation from the current address and verification at the new address.

## Account recovery

With working email, use **Forgot password?** on the login page.

An operator with repository and D1 access can recover an instance from the repository root:

```bash
bun run reset:password -- --email you@example.com --remote --db your-database-name
```

The command prompts for a new password instead of accepting it in the command line. Omit `--remote` for local stores. Without `--db`, remote recovery uses `LINKDEN_DB_NAME`, then `linkden-db`; confirm the intended database before running it.

If both the authenticator and backup codes are lost, add `--disable-2fa`. This resets the password, signs sessions out, and disables two-factor. Enroll again and save new codes afterward.

## Local development login

The bypass is opt-in and local only:

- Put `DEV_LOGIN="true"` in the standalone API's gitignored `apps/server/.dev.vars`.
- Set `NEXT_PUBLIC_DEV_LOGIN=true` in the local frontend environment to show its button.
- Use plain HTTP on loopback hosts for both the configured auth URL and the actual request.

An explicit non-development runtime disables the bypass. Request URL, Host, Origin/Referer, and proxy metadata must pass the local checks. Tunnels and forwarded public hosts cannot establish trust. Better Auth's first-login CSRF middleware still runs. Alchemy does not bind `DEV_LOGIN` into deployed Workers.

Keep local listeners on loopback. The frontend also hides its test prefill and development sign-in on nonlocal pages.

## Uploads and media

Only signed-in administrators can upload. Files are limited to **5 MiB**, with a separate **16 KiB allowance for multipart framing**.

The API requires a valid positive `Content-Length`. It can reject a declared oversized request early, but also counts actual bytes with a bounded buffer before multipart parsing. Understating the header does not bypass the cap.

Accepted extensions are `jpg`, `jpeg`, `png`, `gif`, `webp`, and `ico`; MIME and magic-byte signatures must agree. Invalid files get 400, oversized bodies/files get 413, and a missing length gets 411.

The upload response contains a relative `/api/images/<purpose>/<id>.<ext>` path. The current editor expands it to the configured API origin before saving because URL fields require absolute HTTP(S) values.

Replacement removes only an unreferenced intermediate upload from the same unsaved edit. Saved media is retained when you discard a replacement. The daily orphan sweep reclaims unreferenced objects after a 24-hour grace period; cached copies can outlive storage deletion. JSON backups contain references, not the image files.

Assets-only publication copies individually approved media into hashed public assets. It does not expose the whole R2 bucket or rewrite every historical external URL.

## Validation and secrets

Settings use a shared key allowlist and per-key rules for length, URL, color, enum, or structured data. Blocks validate the resulting type/config together. Backup, wallet, and vCard writes reuse these checks.

Text fields strip real HTML tags; ordinary text such as `x < 5` is preserved. URLs require HTTP(S); publication additionally rejects credentials, whitespace and control characters. Custom CSS is sanitized, and preview CSS is scoped to the public canvas with external fetches removed.

Secret settings are masked when read and excluded from backups. Do not place secrets in `NEXT_PUBLIC_*` variables or exported public artifacts.

## Origin checks and body limits

Write requests to `/trpc/*` and `/api/upload` must pass the trusted-origin/Fetch Metadata checks independently of CORS. Configure `CORS_ORIGIN` to the exact editor origin.

Actual received bytes are capped before parsing:

| Request | Limit |
| --- | --- |
| Auth | 64 KiB |
| Ordinary tRPC, including mixed backup/non-backup batches | 1 MiB |
| tRPC batches containing only `backup.*` procedures | 16 MiB |
| Public contact action | 64 KiB |
| Upload multipart body | 5 MiB + 16 KiB |

tRPC batches allow at most 20 procedure calls. Cloudflare rate-limit bindings protect auth, uploads, contact, vCard, and OG rendering, with IPv6 grouped by /64. Limited batched procedures each spend a token. Better Auth adds its own limiter. These controls are abuse defenses, not hard spending caps; absent optional test bindings do not simulate a provider limit.

## Public and private ingress

The legacy renderer exposes its intentional public page data and form/download routes. Profile view/click collection is retired; legacy collection procedures return NOT_FOUND.

The opt-in split topology keeps the API private behind the admin service binding, except for an explicitly configured public `POST /api/contact` action. That action rejects account credentials, validates the exact public profile origin, requires CAPTCHA, and shares an atomic **100-delivery-reservation UTC daily quota** across contact paths. Failed delivery does not refund a reservation.

Access policies, closed alternate Worker URLs, and cloud ingress tests must be verified before split cutover. Source code alone does not prove those account settings.

## Logging and private downloads

Request logs contain paths rather than token-bearing query strings; password-reset token path segments are redacted. Error logging strips SQL parameters, and API errors omit stack traces and unexpected internals. Workers invocation logs are disabled in the deployment configuration.

Wallet downloads require an admin session and use private, no-store responses. There is no public pass URL. CAPTCHA secrets and signing keys stay server-side; CAPTCHA providers still receive verification data. See [Contact form](/docs/guide/contact-form) for the privacy and delivery setup.
