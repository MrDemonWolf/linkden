---
title: Custom Domain
description: Plan legacy or split hostnames without silently replacing existing DNS and routes.
---


Choose the serving mode before changing hostnames. The default remains legacy; split native publication is a separate opt-in cutover.

## Inspect the existing hostname first

Inventory DNS records, Worker routes/custom domains, certificates, Access policies and alternate Workers URLs read-only. Confirm the account, zone and current owner of each hostname. Do not delete a working DNS record or repoint an existing hostname just to make a deployment succeed.

Cloudflare's [Custom Domains documentation](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/) describes current provider requirements. DNS, routing and certificate changes require explicit operator approval.

## Legacy: one browser origin

```bash
LINKDEN_SERVING_MODE=legacy
SITE_DOMAIN=links.example.com
BETTER_AUTH_URL=https://links.example.com
CORS_ORIGIN=https://links.example.com
NEXT_PUBLIC_SERVER_URL=https://links.example.com
NEXT_PUBLIC_SITE_URL=https://links.example.com
```

Alchemy attaches the web custom hostname and routes `/api/*` and `/trpc/*` to the API Worker on it. Browser cookies stay on that origin. With `SITE_DOMAIN` unset, legacy staging can use the actual web `workers.dev` origin for all four URL values; the web API bridge uses its service binding.

After an approved deployment, verify the profile page, health response, sign-in, 2FA, sign-out and cookie persistence. A health response alone does not prove authentication or public rendering.

## Split: public profile and private admin

For an approved split deployment:

```bash
LINKDEN_SERVING_MODE=split
ADMIN_SITE_URL=https://admin.example.com
PUBLIC_SITE_URL=https://example.com
BETTER_AUTH_URL=https://admin.example.com
CORS_ORIGIN=https://admin.example.com
NEXT_PUBLIC_SERVER_URL=https://admin.example.com
NEXT_PUBLIC_SITE_URL=https://example.com

```

| Host | Responsibility |
|------|----------------|
| `admin.example.com` | Editor and same-origin browser API/auth bridge. |
| `example.com` | Separately published immutable native assets. |
| Optional `api.example.com/api/contact` | Exact POST/OPTIONS public contact action. Other public API paths remain unavailable. |

The public hostname belongs to the separate publisher. Setting `PUBLIC_SITE_URL` does not attach it to an Alchemy Worker, publish content, or authorize DNS changes. The publisher's `PUBLICATION_CONTACT_ACTION` must match the deployed contact action URL.

Protect the admin origin with the intended [Cloudflare Access policy](https://developers.cloudflare.com/workers/configuration/cloudflare-access/) where required. The checked-in IaC does not create that policy. Access protection also requires checking alternate origins and existing version-preview URLs; protecting only the custom hostname is insufficient.

The split deploy guard checks both web/API Workers' `workers.dev` and preview-subdomain settings before provisioning and after finalization. It refuses open aliases instead of closing them silently. The API's only private transport uses its service binding; a hostname check is not a replacement for that network boundary or authentication.

## Cutover checks

Before moving production traffic:

- [ ] Prove the assets-only target serves HTML, bundled images and static 404s without application fallback.
- [ ] Disable the application API in designated staging and confirm the published profile continues working.
- [ ] Verify admin Access, session/2FA behavior and alternate-URL closure.
- [ ] If contact is enabled, test profile-Origin CORS, CAPTCHA, delivery limits and an emergency endpoint-disable procedure.
- [ ] Preserve the last-good public version, database backup/bookmark and tested recovery steps.

These are required verification tasks, not claims that this checkout has passed them in Cloudflare.

## Change or remove a hostname

Treat this as another routing cutover. Review existing resource adoption and Alchemy state first, prepare a rollback, then approve the exact DNS/routes/certificate changes. Preserve existing services until a deliberate migration plan is accepted.

Do not assume that removing `SITE_DOMAIN` or restoring a DNS record reverses every routing, certificate, cookie, data or public-publication change. See [Rollback](/docs/self-hosting/cloudflare#rollback).
