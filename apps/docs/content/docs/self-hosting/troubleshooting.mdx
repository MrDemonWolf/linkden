---
title: Troubleshooting
description: Diagnose local, deployment and publication failures before changing existing data or routes.
---

Start with the exact environment, Worker/resource names and last verified revision. Source configuration, local tests and a green CI run are different from a successful live deployment. See [Cloudflare Deployment](/docs/self-hosting/cloudflare) for the approved deployment flow.

## Deployment configuration fails

The deploy preflight lists missing variables/secrets by name. Check the selected GitHub environment or `packages/infra/.env`; app-specific development files do not configure deployment.

- Legacy mode uses the web origin for auth, CORS, browser API and public site URLs, including a `workers.dev` deployment without `SITE_DOMAIN`.
- `BETTER_AUTH_URL`, `CORS_ORIGIN` and `NEXT_PUBLIC_SERVER_URL` must be bare origins: no path, query or trailing slash. A trailing slash would make the client call `//trpc`, which neither the zone Routes nor the web API bridge match. `NEXT_PUBLIC_SITE_URL` must also be a bare origin, though one trailing slash is allowed.
- Split mode requires separate bare HTTPS admin/public origins, admin auth/CORS/browser API values, public metadata values, and an unset `SITE_DOMAIN`.
- An optional split contact URL must be the exact HTTPS `/api/contact` action on an approved custom hostname distinct from admin.
- Changing the built serving mode or public frontend variables requires a new build.

Do not weaken validation, enable dev login, or point a staging run at production resources to make preflight pass.

## Admin sign-in loops

Check `BETTER_AUTH_URL`, `CORS_ORIGIN` and `NEXT_PUBLIC_SERVER_URL` against the actual browser/admin origin. A trailing slash, different hostname, direct API hostname or changed auth secret can break the session flow.

The web API bridge keeps requests on the web origin through a service binding. `workers.dev` alone is not a reason to configure the browser to call the separate API Worker: on `workers.dev`, all four URL values must be the web Worker's origin (`https://linkden.<workers-subdomain>.workers.dev`). Pointing any of them at the API Worker's `linkden-api` hostname puts the session cookie on a different site (`workers.dev` is on the Public Suffix List), and `/admin` bounces back to `/admin/login`. The deploy preflight refuses auth, CORS and API values that differ from `NEXT_PUBLIC_SITE_URL`. In split mode, also verify the intended Access policy and alternate-URL closure. A successful password response does not prove that the subsequent session/2FA step succeeded.

## Dev login is unavailable

This is expected outside strict local development. The endpoint requires `DEV_LOGIN="true"`, plain-HTTP loopback auth/request/Host values, local Origin/Referer and trusted local proxy metadata. An explicit non-development runtime disables it. The button also requires `NEXT_PUBLIC_DEV_LOGIN` and a local development page.

Tunnels, public hostnames, production pages and edge/proxy headers must not establish trust. Use normal credentials in those environments.

## Authentication is misconfigured

A missing, weak or placeholder `BETTER_AUTH_SECRET` disables auth and protected routes; health reports `auth: "misconfigured"`. Configure a proper private secret and approve the required redeployment. Rotating that secret invalidates sessions.

## Setup is closed or already claimed

An existing admin closes registration with 403 "Registration is closed"; the database enforces the single-admin rule. Go to `/admin/login` rather than resetting the database.

Until an admin exists, `/` and `/admin/login` redirect to `/admin/setup`. There is no setup token: the first signup on an unclaimed public installation becomes the admin, so finish setup right after deploying. If an unknown account claimed a fresh install, treat it as a security incident: export the database for review, then factory-reset the still-empty install (`bun reset:factory -- --confirm --remote`) and complete setup immediately.

For owner-controlled recovery, the repository provides a password-reset command. Confirm the target database before using a remote action; it signs existing sessions out. Add `--disable-2fa` only when deliberately removing two-factor protection after losing both the authenticator and backup codes.

```bash
bun reset:password -- --email you@example.com --remote
```

The password comes from a prompt/stdin or the supported private environment variable, not command-line arguments.

## Database or image binding failures

Inspect the deployed `DB` and `IMAGES_BUCKET` bindings and the exact resource names. The standalone local config is `apps/server/wrangler.jsonc`; cloud deployment uses `packages/infra/alchemy.run.ts`.

Read-only inventory commands from the repository root include:

```bash
bunx wrangler d1 list
bunx wrangler r2 bucket list
```

Older production deployments may need `LINKDEN_DB_NAME` and `LINKDEN_IMAGES_BUCKET` to preserve adoption. Fix the approved configuration and redeploy only after confirming the target. Do not destroy resources or create an empty replacement to repair a missing binding.

## Migrations fail or filenames disagree

Alchemy uses the full `d1_migrations.name` filename and skips names it has already applied. The history runs from `0000` to `0015`; `0011_relative_image_paths` is a data-only rewrite of absolute upload URLs to `/api/images/…` paths (see [Migration history](/docs/self-hosting/cloudflare#migration-history)).

Preserve applied filenames and the current snapshot chain. Do not rename applied SQL files or replay raw SQL loops. Inspect an existing database read-only and test its upgrade/restore in isolation before an approved migration. Never use `drizzle-kit push` to bypass this history.

A local development store created from an unreleased checkout that numbered the contact-quota and publication migrations `0011`–`0014` fails on `0012_parallel_gertrude_yorkes` because `contact_quota` already exists. That only affects local stores: wipe them with `bun db:reset` and apply the migrations again. Never edit ledger rows to silence the error.

## Publishing is off, stuck or failed

- **Publishing off:** check the server's approved target, public origin, renderer SHA and runner configuration. Saving settings does not enable the runner.
- **Draft versus Published:** saved authoring data and block visibility are separate from a verified public publication receipt.
- **Publishing:** do not start another writer or transfer runner ownership while the original job is active. Inspect that exact workflow run and its target.
- **Recovery required:** confirm the interrupted job has stopped, then use the explicit protected recovery operation. It requires a matching last-good immutable version and successful HTTP verification; missing or ambiguous receipts remain unresolved.

Do not label a saved form or successful upload as a live publication.

If old content remains, inspect the active provider version and exact HTTP responses before blaming browser cache. Deleting editor content or resetting D1 does not withdraw an already published native site.

## Public contact is unavailable

In split mode, compare the API's `PUBLIC_CONTACT_URL` with the public publisher's `PUBLICATION_CONTACT_ACTION`. The request must target that exact endpoint, use the configured profile `PUBLIC_SITE_URL` Origin, omit credentials, and pass configured CAPTCHA and limits.

The public endpoint intentionally does not expose auth, health, tRPC, uploads, images or Wallet routes. Do not open a broad `/api/*` route as a workaround. Test the separately approved contact ingress and emergency disable procedure in staging.

## Local preview shows an old interface

An old service worker can retain development JavaScript even after the source changes. Development now retires LinkDen's own root worker and caches, and the updated worker passes loopback requests through. After retirement, reload once more to release the old controller.

If an older worker has not received that update, use the browser's service-worker controls to update or unregister only LinkDen's `localhost` registration, then reload. Keep the database and unrelated site data. Local loopback previews deliberately bypass offline caching; verify deployed offline behavior separately.

## Email does not arrive

Use Settings → Email to configure the supported Resend provider, a valid key and a verified sender. A restored unsupported provider does not send until explicitly changed. Magic links are unavailable without configured email or while two-factor is enabled.

Contact notifications can fall back to the Inbox when delivery fails or email is unavailable. Check the selected delivery setting and server result; a UI preview is not a delivery receipt.

## Uploads or previews fail

- Resize a file rejected by the app's upload size limit.
- Check the supported extension and the actual image signature; renaming an HTML file to `.png` does not make it an image.
- Submit authenticated uploads from the configured admin origin and verify R2 binding/access.
- For static publication, inspect unresolved legacy origins, public upload keys, media byte limits and custom-CSS dependencies. The builder does not fetch arbitrary media to make a candidate pass.
- A Wallet preview is a design preview. Signed downloads additionally require usable certificates, an RSA key, IDs and any needed key passphrase.

## Logs and throttling

The API emits path-only request lines and structured errors, with token-bearing reset segments and Drizzle bound parameters redacted. Invocation logs are disabled in the checked-in IaC. Inspect your provider's actual logging configuration separately.

```bash
bunx wrangler tail linkden-api --format=pretty
```

Daily maintenance reports failed prune/orphan-sweep steps and rejects the scheduled run. Optional publication scheduling has its own outcomes. Inspect the actual cron/workflow result; a configured schedule is not evidence that cleanup or publication succeeded.

A rate-limited request should be retried after its limit window. Limits apply per tRPC procedure in a batch; sign-in also has a global cap.

## Restore or roll back

Take a current export and confirm the exact environment before an approved recovery. Code rollback, database restore and public-version rollback are separate operations.

- [D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/) restores the whole database in place. Check the current provider requirements and chosen bookmark; it can discard newer data.
- The scheduled D1 export goes to `linkden-backups/d1/<date>.sql` with the configured lifecycle. Restore an export into a new isolated database first and verify it before repointing production.
- Preserve migration ledgers, auth constraints and resource adoption settings when restoring. Do not edit ledger rows merely to silence a duplicate-table error.
- Use the publisher's last-good version/recovery flow for native public files; restoring D1 alone does not restore or withdraw those files.

Do not factory-reset an instance as routine troubleshooting. Production restore, deletion, DNS and routing changes require explicit operator approval.
