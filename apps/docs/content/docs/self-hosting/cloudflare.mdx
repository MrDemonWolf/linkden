LinkDen's default deployment uses a Next.js web Worker, a Hono API Worker, D1 and R2. The rebuilt source also includes an **opt-in** split deployment and native static publisher. Building this checkout does not activate that publisher, change routing, or prove a live deployment.

## Serving modes

| Mode | Public page | Browser API and sign-in | Publication |
|------|-------------|-------------------------|-------------|
| `legacy` (default) | Next.js renders saved profile data | Same web origin; service binding reaches the API | Existing dynamic behavior |
| `split` (opt-in) | A separate native-assets target serves a frozen revision | Approved admin hostname; API stays behind its service binding | Explicit build, activation and HTTP verification |

## Before deploying

- Install the Bun version declared by `package.json` and Node.js 24. Alchemy runs under Node; use the repository's installed tooling.
- Identify the exact Cloudflare account, environment, resource names and hostnames. Inspect existing resources before creating or adopting them.
- Review your account plan, CPU budget and shared allowances. This guide does not guarantee Free-plan compatibility or a particular bill.
- Obtain approval for production deployment, DNS, routes, certificates, billing changes and destructive recovery. Designate isolated resources before a staging deployment.
- For GitHub deployment, configure the `production` environment's required reviewer and selected deployment branch `main`. Workflow source guards do not create those environment protections.

```bash
git clone https://github.com/MrDemonWolf/linkden.git
cd linkden
bun install --frozen-lockfile
cp .env.example packages/infra/.env
```

The example file starts with local HTTP URLs. Replace them with your chosen deployment configuration before deploying.

## Configure deployment

Use the [environment reference](/docs/self-hosting/environment-variables) for the complete variable list. A new legacy deployment with an approved custom hostname uses:

```bash
LINKDEN_SERVING_MODE=legacy
SITE_DOMAIN=links.example.com
BETTER_AUTH_URL=https://links.example.com
CORS_ORIGIN=https://links.example.com
NEXT_PUBLIC_SERVER_URL=https://links.example.com
NEXT_PUBLIC_SITE_URL=https://links.example.com
```

Set `BETTER_AUTH_SECRET`, `SETUP_TOKEN`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `ALCHEMY_PASSWORD` and the appropriate Alchemy state configuration privately. Generate separate random secrets with:

```bash
openssl rand -base64 32
```

Scope the Cloudflare token to the selected account and zones. The existing IaC needs access to Workers, D1 and R2; custom-domain and route changes also need the relevant zone, DNS, route and certificate permissions. Use the provider's current permission names and grant only the resources required for the approved operation.

A deployment reads `packages/infra/.env` or CI values. It does not use `apps/web/.env` or `apps/server/.env`. The preflight rejects missing values, weak auth secrets, non-HTTPS deployment URLs and mismatched origins before provisioning.

For legacy `workers.dev` staging, use the **actual web Worker origin** for all four URL variables. Find the Workers subdomain in your account; do not infer it from the account name. Browser calls use the web origin's API bridge, not the API Worker's separate hostname. Verify sign-in and cookies in that environment.

### Alchemy state

The checked-in program uses MrDemonWolf's shared `alchemy-state` Worker and `ALCHEMY_STATE_TOKEN`. Third-party self-hosters must configure their own state store; they cannot use that account's store by copying the example.

Keep `ALCHEMY_PASSWORD` and the state store available for later deployments. Review the [Alchemy state-store documentation](https://alchemy.run/state-store) against the installed package version before changing stores; current website API examples can differ from this checked-in program. `ALCHEMY_STAGE` defaults to `prod`; other stages use suffixed resource names. Confirm those names and the state namespace before acting.

### Upgrading a deploy made before 0.5.0

Older deployments may have generated D1 and image-bucket names. Set `LINKDEN_DB_NAME` and `LINKDEN_IMAGES_BUCKET` to the **existing** names before an approved production upgrade. These overrides apply only to `prod`; other stages ignore them.

```bash
LINKDEN_DB_NAME=linkden-database-runner
LINKDEN_IMAGES_BUCKET=linkden-images-runner
```

Export the database and inventory uploaded objects before changing adoption or state configuration. A new empty database would reopen first-run setup. Do not destroy an old stage to repair adoption.

### Migration history

Alchemy tracks **full SQL filenames** in `d1_migrations`, not just their numeric prefixes. Preserve applied filenames and the current Drizzle snapshot lineage. This checkout's history runs from `0000` to `0014`; its `0011_parallel_gertrude_yorkes.sql` and a dev ledger's `0011_relative_image_paths.sql` are different identities, and an extra already-applied ledger entry is tolerated.

Do not blindly merge or replay the older image-path rewrite. It matches URL paths without proving the host belongs to this instance and could alter external images. The current history does not automatically normalize those URLs. Inventory legacy upload origins before deciding whether a data migration is needed. Local upgrade tests do not replace an approved staging migration and restore test.

## Deploy and initialize

Once the target, configuration and changes are approved:

```bash
bun run deploy
```

This applies pending migrations and provisions or updates the selected web/API Workers, D1 and R2 resources. It is a cloud mutation, not a preview command.

1. Read the actual output and verify `/api/health` through the web/admin origin.
2. Open `/admin/setup` on that origin and supply `SETUP_TOKEN` to create the sole admin account.
3. Enable two-factor authentication in Settings → Account and save backup codes.
4. Verify sign-out, password sign-in, the TOTP/backup-code step and session persistence.

The database enforces one admin. Without a setup token, the first person to finish setup can claim a new public instance.

## Split deployment and public publication

`LINKDEN_SERVING_MODE=split` is an explicit routing cutover. It requires distinct `ADMIN_SITE_URL` and `PUBLIC_SITE_URL`, with `SITE_DOMAIN` unset. Auth, CORS and browser API URLs use admin; public metadata uses the public origin. See [Custom Domain](/docs/self-hosting/custom-domain) for an example.

The server has no public API routes by default in split mode. An optional `PUBLIC_CONTACT_URL` exposes only one exact HTTPS `/api/contact` action on an approved custom hostname distinct from admin. The public site's Origin is checked independently. CAPTCHA, credential rejection, body limits, client throttling and the daily submission quota remain in force.

Before cutover, configure and verify admin access protection, close alternate Workers and version-preview URLs, test contact ingress and its emergency disable procedure, and prove public delivery while the application API is unavailable. IaC flags and a successful build are not proof of those boundaries.

### Publish public revisions

The publisher uses frozen approved source, bundled public uploads and generated social images. Saving authoring data does not replace the last verified public version. Failed or ambiguous activation requires verified rollback or explicit recovery; it must not be labelled Published.

The workflow uses separate `public-staging` and `public-production` GitHub environments, owner opt-in, an approved exact `main` renderer commit with successful CI, and serialized runs per target. Configure their protections and the [publisher variables](/docs/self-hosting/environment-variables#public-publisher-environments) deliberately.

The runner, dispatcher and workflow currently restrict automation to `MrDemonWolf/linkden`. Forks must review and adapt those repository checks before using automated publication. `bun run build:public` only builds local artifacts; it is not a production deployment command.

Optional five-minute publication ticks use the previously approved immutable source. They do not reread mutable drafts or rebuild on every tick. Profile analytics collection remains retired.

## GitHub deployment and backups

`.github/workflows/deploy.yml` deploys after successful CI for a push to this repository's `main`, uses the `production` environment, and does not cancel a running deploy. Store secrets and variables in that approved environment using the [reference](/docs/self-hosting/environment-variables). Its preflight, restore-point capture and smoke probes can fail; inspect each actual result.

`backup-db.yml` schedules a D1 export into `linkden-backups` and refuses a dump with no admin row. The configured R2 lifecycle expires these exports after 30 days. Verify a real export and an isolated restore before depending on it. JSON exports from Settings → Data contain references to uploaded images, not the image files themselves.

## Resource use

These are source-derived application operations, not measured invoices:

| Request reaching the deployment | Application work |
|--------------------------------|------------------|
| Legacy anonymous profile render | Web Worker + API service-binding execution; four D1 SELECTs in one batch |
| Legacy uploaded image | Image handler; an R2 read on a cache miss, with an additional web hop when proxied |
| Native published HTML, bundled asset or static 404 | Zero application Worker executions, D1 queries or R2 reads on that delivery path |

The native row requires an assets-only target with no application fallback or Worker-first routing, and Workers Cache disabled. External media has its own requests. Admin/auth activity, contact forms, publication builds and media reads, daily maintenance, optional schedule ticks and backup jobs still consume resources.

Cloudflare distinguishes static asset delivery from Worker script execution in its [current asset billing documentation](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/). Shared account usage, billed D1 rows, CPU time, storage and retries must be measured separately. No verified account plan, Free-plan CPU result or savings estimate is implied here.

## Rollback

Preserve an export, the exact deployed code/version IDs, the D1 bookmark and a tested recovery procedure before cutover.

- A web/API code rollback does not undo database changes. Confirm schema compatibility with the version being restored.
- D1 Time Travel rewinds the entire database. Check the provider's [current Time Travel documentation](https://developers.cloudflare.com/d1/reference/time-travel/) and the exact database/bookmark before an approved restore.
- Public publication uses its recorded last-good immutable version and HTTP checks. Explicit interrupted-job recovery restores that version rather than publishing mutable drafts. A missing last-good receipt remains a recovery gate.
- Deleting editor content or resetting its database does not withdraw files already published to the separate native target. Replace or disable that target through the approved publication/operations procedure.

Production deployment, DNS, routing, billing and destructive recovery remain explicit operator decisions. See [Troubleshooting](/docs/self-hosting/troubleshooting) for diagnosis before changing resources.
